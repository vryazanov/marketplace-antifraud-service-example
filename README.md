# Marketplace Antifraud Service

Первый этап задания «Маркет: антифрод с Jev AI»: отдельный Python 3.13 сервис
с PostgreSQL и Jev через LLM-шлюз LMS. Это экспериментальная политика, не оценка
качества Jev на реальном мошенничестве. Полная интеграция с Маркетом ещё не готова.

## Слои

- `domain`: снимок объявления, пять сигналов, решение и политика.
- `application`: порты классификатора, репозитория и UoW; use case проверки.
- `infrastructure`: httpx-адаптер Jev, SQLAlchemy и PostgreSQL advisory locks.
- `presentation`: FastAPI, схемы и внутренний HTTP API.

Domain/application не импортируют FastAPI, SQLAlchemy, httpx или Kafka.
Сборка зависимостей — `src/fastapi.py`. У сервиса собственная БД.

## Разработка

```bash
uv sync --frozen --python 3.13
uv run ruff check src/ bin/
uv run ruff format --check src/ bin/
uv run pytest tests/ -q
```

Скопируйте `.env.example` в игнорируемый `.env` и локально задайте отдельный
`LMS_LLM_API_KEY` провайдера typesafe, полученный у ментора. Ключ управления
VLMS не подходит. Без ключа сервер запускается, но новая проверка возвращает
503; положительное решение не подставляется автоматически.

```bash
docker compose up -d --build
```

API доступен на localhost:8004, PostgreSQL — localhost:5436. Compose выполняет
миграции отдельно перед API. Для запуска из Python после старта БД:
`uv run alembic upgrade head`, затем `uv run python -m bin.api` (порт 8000).
В общем Compose лаборатории API/БД доступны только во внутренней сети.
Ключ для общего Compose берётся из окружения корня, например:
`docker compose --env-file services/marketplace-antifraud-service-example/.env up -d --build`.
Не выводите развёрнутый Compose с подставленными секретами; для проверки —
`docker compose config --quiet`.

## Внутренний контракт

`POST /internal/checks`: `ad_id`, `user_id`, `title`, `description`, `price`,
`category`, `city`. Маршрут предназначен только для доверенных сервисов,
не публикуется через общий фронтенд или Ingress.

Ответ: `status` (`allowed` или `blocked`), `reason` (непустая строка при blocked),
`categories`, `content_hash`, `policy_version`, `checked_at`, `fraud_ads_in_week`
и `soft_delete_required`. Последний флаг — требуемое действие интеграции,
а не подтверждение, что аккаунт удалён. Синхронная проверка может занять время
до таймаута Jev. До сохранения результата вызывающая сторона должна проверить,
что `content_hash` относится к текущей версии объявления, а не к устаревшей.

Проверяем пять `noul`-вопросов. Порог 0.85 — предварительный и настраивается
через `ANTIFRAUD_THRESHOLD`. Объяснения формируются из фиксированных понятных
текстов, а не из выдуманного ответа генеративной модели. Ошибка, таймаут,
неполный или некорректный ответ Jev дают 503 без сохранения решения.

Одинаковые ad/user/content/policy используют сохранённую проверку. PostgreSQL
transaction advisory lock сериализует проверки одного продавца, в том числе
параллельные, чтобы не дублировать оплату и считать нарушения последовательно.
Транзакция держится во время вызова Jev: для первой версии выбран простой
синхронный подход; для высокой нагрузки нужна очередь/состояние pending.
Отмена запроса освобождает транзакцию; автоматических платных ретраев нет.

Считаются различные fraud-объявления за скользящие семь суток по времени
первой проверки конкретной версии. Повтор запроса не обновляет время нарушения.
Спам/реклама/угрозы/насилие сами по себе не увеличивают fraud-счётчик.
История нарушений сохраняется после исправления объявления; три разных
объявления с fraud в окне дают `soft_delete_required=true`.

`GET /health` проверяет БД и сообщает только факт настройки ключа, не тратя
бюджет модели. Готовность БД не доказывает наличие бюджета или работу Jev.

## Датасет и эксперименты

Датасет и порядок экспериментов — `docs/antifraud/` мета-репозитория.
Из каталога сервиса явно запустите платную команду:

```bash
uv run python -m bin.evaluate --dataset ../../docs/antifraud/dataset.jsonl \
  --split train --output ../../docs/antifraud/train-results.json
```

Каждый пример расходует пять вопросов. Файл содержит версию/вопросы политики,
хеш датасета, фактическую модель, сигналы, usage, сравнение с разметкой и baseline.
Команда не перезаписывает существующий отчёт; частичный результат сохраняется
при ошибке. Оценка на holdout выполняется отдельно после выбора политики.
Реальных результатов пока нет: ключ ещё не предоставлен, разметка не проверена.

## Что ещё требуется для выполнения курса

В Ad нужно добавить blocked/reason, применение решения с проверкой версии,
Outbox и выдачу статуса в «Моих объявлениях». В Search — исключение blocked
из индекса. В Auth — идемпотентный soft delete, запрет входа и refresh для
удалённых аккаунтов; существующий физический DELETE применять нельзя.
Эти интеграции не внесены, готовность задания не заявляется.

## Контейнер и проверки БД

Dockerfile запускает процесс от UID 1000 на порту 8000. `bin.start` применяет
миграции до запуска API и передаёт ему SIGTERM через exec. Локальный Compose
разделяет миграции и API. `POSTGRES_CONNECTION_STRING` приводится к asyncpg.

Для интеграционных тестов нужна отдельная PostgreSQL с применёнными миграциями.
Задайте `TEST_DATABASE_URL`; тесты используют только собственные уникальные ID
и очищают только созданные ими проверки. Без переменной эти тесты пропускаются.
`docker compose down` сохраняет том; `down -v` удаляет данные и требует намерения
сбросить окружение.
